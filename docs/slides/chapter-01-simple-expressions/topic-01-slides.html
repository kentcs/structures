Vertex’s Expression Grammar

expression = term { ("+" | "-") term }
term = factor { ("*" | "/") factor }
factor = <number> | "(" expression ")"

Extended Backus-Naur Form (EBNF)

Braces repeat. A vertical bar separates alternatives.

Quoted punctuation is actual language syntax. Grammar names identify larger pieces. A single number qualifies as a factor, term, and expression. Expression asks for complete terms; term asks for complete factors. Multiplication precedence comes from that call structure. factor has no unary alternative: -5 fails, 0-5 works. Parentheses recurse to a full expression.

The right subtree supplies 20 to the addition.

Parentheses Re-enter the Grammar

if token["tag"] == "(":
    node, tokens = parse_expression(tokens[1:])
    if tokens[0]["tag"] != ")":

(3+4)*5 groups the addition first.

Consume opening parenthesis, parse inner expression, require and consume closing parenthesis. Return inner node directly. The expression helper leaves closing parenthesis for the factor caller. Recursion permits nested parentheses. No explicit parenthesis node in evaluator. Reference background: https://en.wikipedia.org/wiki/Recursive_descent_parser.

Building a Term

left, tokens = parse_factor(tokens)
while tokens[0]["tag"] in ["*", "/"]:
    op = tokens[0]["tag"]
    right, tokens = parse_factor(tokens[1:])
    left = {"tag": op, "left": left, "right": right}
return left, tokens

8/4/2 builds (8/4)/2 and returns 1.0.

Body of parse_term. Previous tree becomes the next node's left child. That loop establishes left associativity. Different from 8/(4/2), which returns 4.0. parse_expression uses the same loop pattern for plus/minus but requests terms as operands. Precedence is between levels. Associativity is grouping within a level. Division and subtraction distinguish grouping more clearly than addition.

Requiring the Whole Expression

ast, tokens = parse_expression(tokens)
if tokens[0]["tag"] is not None:
    raise SyntaxError(f"Unexpected token: {tokens[0]}")
return ast

3 4 must fail after the parser reads 3.

Body of public parse function. A helper can successfully parse a prefix without validating all input. At top level the end marker is required. Inside parentheses, the caller instead expects a closing parenthesis. This is why helper and public-parser contracts differ. Runner calls parse, not just parse_expression.

Evaluating the Tree

if ast["tag"] == "number":
    return ast["value"]
elif ast["tag"] == "+":
    return evaluate(ast["left"]) + evaluate(ast["right"])
elif ast["tag"] == "*":
    return evaluate(ast["left"]) * evaluate(ast["right"])

For 3+4*5: the children supply 3 and 20.

Excerpt from evaluate omits subtraction, division, and unknown-node error. Number is base case. Operator recursively evaluates its children then applies Python arithmetic. Grouping is already in tree, so evaluator needs no precedence table or parenthesis scan. Python numeric behavior supplies semantics: true division, floating-point rounding, division-by-zero exception. Syntax rules belong to Vertex even though Python provides these operations.

Where an Expression Fails

Input Failure Stage

3+*4 Missing operand Parser
(3+4 Missing closing parenthesis Parser
-5 No unary negation rule Parser
3/0 Division by zero Evaluator
Rejecting invalid input is required behavior. Valid tokens do not guarantee valid syntax. Valid syntax does not guarantee successful evaluation. Unexpected token errors include dictionaries with source locations; tokenizer error currently reports character without location. Unknown AST node ValueError is a separate guard for malformed trees supplied to evaluator.
