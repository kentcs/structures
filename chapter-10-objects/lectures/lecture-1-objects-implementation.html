Copying Is New, Not Generalized

vertex_copy and its memo dict do not exist in Chapter 9 at all: no copy keyword, no deep-copy helper, nothing to widen. Lists only ever got vertex_equal and vertex_repr.

What carries over is the idea, not the code: track identities on a mutable structure, adding an entry before recursing into it. comparing and ancestors remove their entry on the way back out, since they only need to know what is on the current path. memo keeps every entry for the whole copy() call, since a sibling reached later still needs to find it.

Without a Memo Table, Sharing Breaks

data’s two arrows reach one child. A copier with nothing to remember what it has already copied cannot tell its second arrow is the same original as its first; it produces two unrelated copies instead of one shared one.

The Memo Table Keeps Them One

The table itself: one entry, child’s identity mapped to its copy. Both of mycopy’s arrows land on that one entry’s value. The dashed arrow is a computed lookup by id(child), not a stored reference; the solid arrows are the real references.

The Memo Table, Proof

child = {"x": 1};
data = [child, child];
mycopy = copy(data);
mycopy[0].x = 99;
print(data[0].x);
print(mycopy[1].x);

data[0].x stays 1: the copy did not reach back into the original. mycopy[1].x becomes 99: mycopy[0] and mycopy[1] are still the same object.

The Same Table Closes a Cycle

a = {};
a.self = a;
b = copy(a);

The memo table’s second job: a has no base case for a naive copier, since copying a.self means copying a again, forever.

What Carries Forward

The "complex" node absorbed a second suffix kind with one new branch in one existing loop, not a second grammar. vertex_equal and vertex_repr absorbed a second container kind the same way: widen a type check, reuse the cycle-safety bookkeeping as written. vertex_copy is different: it is new code, for a need Chapter 9 never had, that reuses the same identity-tracking idea rather than any existing implementation. The one new question this chapter answered was growth, when is a destination allowed to gain a key it never had, and the answer differs by container on purpose. Chapter 9 already asked what “the target” means when it is not just a name; this chapter answered it a second way, by string key instead of position, and left that same question open once more, for call arguments, next.
